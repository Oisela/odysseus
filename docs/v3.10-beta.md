## Neue Funktionen

### Developer-Live-Status

Die Developer-Hauptseite zeigt CPU, Load, Kernanzahl, RAM, Datenträger,
Uptime und die Quelle der Messung.

- Automatische Aktualisierung alle fünf Sekunden, solange das
  Developer-Fenster sichtbar ist.
- Der Refresh-Knopf erzwingt eine neue Messung.
- Ein vier Sekunden kurzer Server-Cache verhindert parallele SSH-Probes.
- Wenn die Host-Abfrage nicht möglich ist, wird sicher auf Messwerte des
  App-Containers zurückgefallen.
- Die API liefert nur aggregierte Auslastungswerte. Prozesslisten,
  Kommandozeilen, Umgebungsvariablen oder andere sensible Hostdaten werden
  nicht übertragen.

API: `GET /api/system/metrics`, erzwungene Messung mit
`GET /api/system/metrics?refresh=1`.

### Roadmap-Board und Versionsworkflow

- Listen- und Board-Ansicht besitzen eine kompakte, responsive Werkzeugleiste.
- Die Spalte **Erledigt** zeigt nur die letzten zehn Einträge.
- Die Zielversion eines geplanten Eintrags kann direkt bearbeitet werden.
- Alle geplanten Einträge können gesammelt einer Zielversion zugewiesen
  werden.
- Beim Start eines Builds wechselt der Eintrag sofort auf `[~]`.
- Schlägt das Erstellen des Builder-Chats fehl, werden Build-Datensatz und
  Roadmap-Status zurückgerollt. Dadurch bleibt kein falscher
  „In Arbeit“-Eintrag hängen.

Build-Datensätze werden über
`/api/system/roadmap/builds` angelegt, gelesen und bei einem Rollback wieder
gelöscht.

### Minimierte Fenster innerhalb des Chats

Minimierte Fensterchips leben ausschließlich im Chatbereich und nicht mehr
über Sidebar oder Hauptnavigation.

- Chips und Chip-Gruppen sind frei verschiebbar.
- Positionen werden relativ zum Chat gespeichert.
- Bei Größenänderung, Sidebar-Wechsel und Composer-Höhenänderung werden
  Positionen neu begrenzt.
- Freie Pixelpositionen deaktivieren die Zentrier-Transformation des
  Standard-Docks. Dadurch kann eine korrekt begrenzte Gruppe nicht nochmals
  unter die Sidebar verschoben werden.
- Sehr lange Chip-Titel werden innerhalb der verfügbaren Chatbreite mit
  Auslassungszeichen gekürzt.
- „Dock home“ baut abgetrennte Einzelchips wieder als Kinder der gemeinsamen
  Dock-Gruppe auf. Der Layout-Sync erkennt und repariert zusätzlich
  verwaiste absolute Chips ohne gespeicherte freie Position.
- Der Composer bleibt frei und wird nicht von Chips überdeckt.
- Ein DOM-Observer ersetzt dauerhaftes Polling und reduziert die allgemeine
  UI-Last.
- Bereits vorhandene Minimieren-Knöpfe werden vom zentralen Modal-Manager
  übernommen, sodass nicht zwei Minimize-Systeme gegeneinander arbeiten.

Gespeicherter Browserzustand:
`odysseus.chatDockState.v2`.

### Auswählbare Notes-Tags

Das freie Label-Feld wurde durch eine Tag-Auswahl ergänzt:

- vorhandene Tags auswählen,
- mehrere Tags gleichzeitig verwenden,
- neue Tags direkt anlegen,
- Tags als Chips sehen und einzeln entfernen,
- Bedienung in normaler und mobiler Vollbildansicht.

Die Speicherung bleibt rückwärtskompatibel. Tags werden weiterhin
normalisiert als leerzeichengetrennte Werte im vorhandenen `label`-Feld
gespeichert. Ein Cache hält bekannte Tags auch beim Wechsel zwischen aktiven
und archivierten Notizen verfügbar.

### Kompakter Pomodoro-Fokusmodus

Chromium-basierte Browser können den Timer als Always-on-top
Document-Picture-in-Picture öffnen.

- Start, Pause, Fortsetzen und Überstunden direkt im Fokusfenster.
- Fortschrittsring, Restzeit sowie Tages- und Wochenfokus.
- Einklappbare Minimalansicht.
- Kompakte, zentrierte TickTick-artige Oberfläche ohne leeren unteren Bereich.
- Der Einklapp-Knopf besitzt einen eigenen Platz und überlappt den Phasentext
  nicht mehr.

Chromium besitzt die äußere PiP-Titelleiste und kann eine Mindestgröße
erzwingen. Odysseus kann deshalb Form und Inhalt des Fensters gestalten, aber
nicht die native Browserleiste entfernen oder eine exakte Bildschirmposition
garantieren. Nach einem CSS-Update muss ein bereits geöffnetes PiP-Fenster
geschlossen und neu geöffnet werden, weil es Styles beim Öffnen kopiert.

## Beta-Testanleitung

1. Beta über
   `https://odysseus-server.tailec54cf.ts.net:7001/` öffnen.
2. Mit einem Admin-Konto die Developer-Hauptseite öffnen.
3. CPU/RAM/Disk/Uptime beobachten und den manuellen Refresh testen.
4. Roadmap zwischen Liste und Board umschalten.
5. Eine Zielversion einzeln ändern und die Sammelzuweisung testen.
6. Einen Testeintrag bauen und prüfen, dass er sofort in **In Arbeit**
   erscheint.
7. Zwei Werkzeuge minimieren, Chips verschieben und Sidebar/Chatgröße ändern.
8. In Notes vorhandene Tags wählen, ein neues Tag anlegen und wieder
   entfernen.
9. Pomodoro öffnen, das Fokusfenster starten, pausieren, einklappen und wieder
   ausklappen.

Bei einem Fehler bitte Screenshot, Uhrzeit, betroffene Seite und die genaue
Aktion festhalten. Damit kann der passende Container-Logabschnitt eindeutig
zugeordnet werden.

## Beta-Deployment

### Isolation

Der Beta-Checkout liegt unter `/opt/odysseus-beta`.

- eigene App-Daten unter `/opt/odysseus-beta/data`,
- eigene Chroma-Instanz `chromadb-beta`,
- eigener Session-Cookie,
- Kanal `ODYSSEUS_CHANNEL=beta`,
- Code-Mounts read-only aus dem Beta-Checkout,
- Tailscale HTTPS vor dem intern gebundenen App-Port.

`docker-compose.override.yml` ist eine lokale, nicht eingecheckte
Deployment-Datei. Sie muss bei Git-Arbeiten erhalten bleiben. Insbesondere
darf ein Stash mit `--include-untracked` diese Datei nicht unbemerkt aus dem
aktiven Checkout entfernen.

### Sicherer Netzwerkpfad

Beta lauscht intern:

```dotenv
APP_BIND=127.0.0.1
APP_PORT=7001
```

TLS und Tailnet-Zugriff übernimmt Tailscale Serve:

```bash
tailscale serve --yes --bg --https=7001 http://127.0.0.1:7001
tailscale serve status
```

Der App-Port wird dadurch weder ans öffentliche Internet noch unverschlüsselt
an alle Netzwerkinterfaces gebunden.

### Code aktualisieren

Vor jedem Update zuerst prüfen und lokale Änderungen sichern:

```bash
cd /opt/odysseus-beta
git status --short --branch
git fetch origin feat/notes-wysiwyg
git merge --ff-only origin/feat/notes-wysiwyg
```

Frontend- und Python-Code sind read-only gemountet. Reine
Frontend-Aktualisierungen benötigen deshalb normalerweise keinen Image-Build.

Bei Änderungen an `requirements.txt`, `requirements-optional.txt`,
`Dockerfile` oder dem Entrypoint muss das Beta-Image neu gebaut werden:

```bash
docker compose -p odysseus-beta up -d --build --no-deps \
  odysseus chromadb-beta
```

### Health-Checks

```bash
curl -fsS https://odysseus-server.tailec54cf.ts.net:7001/api/version
docker ps --filter name=odysseus-beta-odysseus-1
docker logs --since 5m odysseus-beta-odysseus-1
docker exec odysseus-beta-odysseus-1 python -m pip show mcp
```

Erwartet werden Version `3.10.0`, Kanal `beta`, ein laufender Container und
eine MCP-Version kleiner als 2.

### Rollback

1. Lokale Änderungen und die nicht eingecheckte Compose-Override-Datei
   sichern.
2. Einen zuvor geprüften Commit in einem separaten Beta-Branch auschecken.
3. Bei reinen Codeänderungen die Seite neu laden; bei Dependency- oder
   Imageänderungen den Beta-Dienst neu bauen.
4. `/api/version`, Logs und die Kernfunktionen erneut prüfen.

Keine Produktionsdaten kopieren und niemals den Produktionscontainer für
einen Beta-Rollback neu erstellen.

## Qualitätssicherung

- 45 relevante UI-, Backend- und MCP-Regressionstests bestanden auf dem
  aktuellen isolierten Beta-Stand `639e268`.
- Darin enthalten sind zwölf Minimize-/Dock-Regressionstests sowie der
  eigene Test für den MCP-Pin.
- JavaScript-Syntaxchecks bestanden für alle geänderten Module.
- `git diff --check` blieb sauber.
- Der zuletzt vollständige Lauf auf `f31ad16` meldete 4.641 bestandene und
  4 übersprungene Tests. Nach den beiden abschließenden Dock-Fixes wurde die
  aktuelle 45-Test-Suite erneut ausgeführt.
- Sechs Fehler in unveränderten Backend-/Prompt-Bereichen bleiben separat
  zu untersuchen und werden nicht als v3.10-Erfolg ausgegeben.

Der abschließende Review beseitigte unter anderem:

- doppelte Minimize-Ereignisse,
- unnötiges periodisches Modal-Scanning,
- außerhalb des Chats liegende Dock-Positionen,
- über dem Composer liegende Chips,
- verlorene bekannte Tags nach Archivwechsel,
- falsche `[~]`-Zustände nach fehlgeschlagenem Chat-Start,
- uneinheitliche Sortierung der Erledigt-Spalte,
- parallele beziehungsweise zu häufige Host-Metrik-Probes,
- eine ungeschützte MCP-Major-Aktualisierung.
